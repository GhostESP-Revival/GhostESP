# GhostESP documentation site

The docs site is Hugo with a custom theme (`themes/ghostesp`) and a **Pagefind** search
index. The built output in `public/` is committed to the repository, so it must be
regenerated whenever content, layouts, CSS, or JS change.

## Build

```bash
npm install          # once, installs Pagefind
npm run build        # hugo --minify --cleanDestinationDir && pagefind --site public
```

`npm run build` writes the site to `public/` and then indexes it into `public/pagefind/`.
Commit both.

If you already have a current `public/` and only need to rebuild the search index:

```bash
npm run search       # pagefind --site public
```

## Local preview

```bash
npm run serve        # hugo server
```

Search does not work under `hugo server` because Pagefind indexes the built output, not
the live dev server. To test search locally, run `npm run build` and serve `public/`
with any static file server.

## How search is wired

- `data-pagefind-body` on `<main>` in `themes/ghostesp/layouts/_default/baseof.html`
  scopes the index to page content. The topbar, sidebar, and footer carry
  `data-pagefind-ignore` so navigation text never shows up as a result.
- `data-pagefind-filter="version:<id>"` on the app wrapper tags every page with its
  firmware version, which is what the sidebar's version scoping and the search page's
  version dropdown filter on.
- `data-pagefind-meta` on `<main>` carries the section name and the plain-text
  (`index.txt`) URL used by the search page.
- `assets/js/search.js` (sidebar) and `assets/js/search-page.js` (the `/search/` page)
  call the Pagefind JS API directly and render results themselves, including Pagefind's
  `sub_results` so hits deep-link to the matching heading.
- Attribute names must not collide: the sidebar input carries `data-search-page-url`
  (its target URL, read by `search.js`) while the search page container carries the bare
  `data-search-page` marker (read by `search-page.js`). Both were once
  `data-search-page`, and because the sidebar input appears first in the DOM,
  `document.querySelector('[data-search-page]')` returned the input, so the search page
  script failed its element check and never wired up search. `search-page.js` now
  resolves its container from `[data-search-page-results]` via `closest()`.

## Result deep links and highlighting

- On load, both search UIs call `pagefind.options({ highlightParam: "highlight" })`, so
  Pagefind stamps result URLs with `?highlight=<query>`.
- A result whose page has matching sections links to the **matched heading**, for example
  `/latest/lora/commands/?highlight=autostart#boot-auto-start`. Pagefind returns
  `sub_results` in document order, so the code picks the first entry that has an anchor
  *and* whose `excerpt` contains a `<mark>`, which is the section the query actually hit,
  falling back to the page URL.
- `themes/ghostesp/layouts/_default/baseof.html` conditionally imports
  `/pagefind/pagefind-highlight.js` and creates a `PagefindHighlight` only when the URL
  carries `?highlight=`, so normal page loads never fetch that bundle. Pagefind marks
  text inside `[data-pagefind-body]` and skips `[data-pagefind-ignore]`, which keeps the
  sidebar, topbar and footer clean.

The JSON outputs (`search-index.json`, `index.json`, and the per-version files) are a
separate, documented API for AI agents and tooling. They are generated by Hugo and are
unrelated to the Pagefind index.
